# Assumptions

These are my design decisions. The backend, admission UI, and container images are implemented; Compose startup is still pending.

- I treat each grade/shift as a separate class. I chose UUIDs rather than the sample `c_123`/`h_789` prefixes. Class names are case-sensitive, limited to 200 characters, and trimmed before validation; duplicates return 409.
- I kept the 17-digit check in the React plan. The API accepts one trimmed, non-empty `X-Student-Id` up to 64 characters, including synthetic IDs such as `student-1`. I store it as `VARCHAR(64)` to preserve leading zeros and case. Hold creation needs no body; I reject unknown body fields so identity cannot be supplied in two places.
- I apply the duplicate rule per class: one active hold or confirmed admission per student. Different classes are allowed. Expired/cancelled applications stay in history, with their expiry timestamps; reapplying creates a new row. I list history newest first, then by UUID for ties. Confirmed admissions cannot be cancelled.
- I treat the payment button as successful payment. Repeating confirmation returns the same confirmed result (200); repeating an owned cancellation returns 204. Neither retry creates another admission.
- I chose 403 when a valid student ID tries to confirm/cancel another student's hold, and 404 for an unknown hold. Ownership is checked before changing state.
- I chose 409 for cancellation of an expired or confirmed application. If a stored `HELD` row is already overdue, confirm/cancel must save `EXPIRED` and commit before returning 409. It must not become `CANCELLED` or have its expiry update rolled back.
- I use PostgreSQL `clock_timestamp()` after acquiring locks for expiry checks and expiry calculation. Equality with `expires_at` means expired. Holds default to 600 seconds through `HOLD_DURATION_SECONDS`. I chose one expiration batch per second, up to 100 rows, with configurable limits and `SKIP LOCKED` so workers can share the workload without waiting on busy holds.
- I interpret first-come, first-served as database allocation-lock order, not browser-click time. Counts come from active holds plus confirmed rows. Creation expires stale `HELD` rows before checking the partial unique index. Failed allocation rolls back that cleanup with the rest of its transaction; summaries still exclude overdue rows.
- I remember only a validated 17-digit student ID in `localStorage`, restore it on startup, and fetch `/me/holds`; I do not cache application statuses locally. I refresh visible history every 2.5 seconds while it contains a hold. This leaves a sensitive ID on shared devices, so I show a notice and mask it on screen. Forget/Change clear the saved selection and history and cancel pending loads; late responses are ignored. Blocked storage permits temporary access with a warning. IDs stay out of logs and URLs.
- I treat the countdown as a display aid. I anchor the server's remaining duration to a monotonic timer and deduct the full request round trip, accepting a slightly early cutoff. The UI polls active details, disables payment at estimated expiry, and fetches backend status before showing EXPIRED. The browser clock cannot authorize payment.
- I leave `POST /classes` unauthenticated for this demo and preserve header-free `GET /holds/{holdId}`. The header and UUIDs do not authenticate anyone; knowing an ID can expose status or allow impersonation. Real deployment would need authentication.
- I chose services using scoped `AppDbContext` directly, without repository wrappers. The frontend container writes runtime `config.json` from `API_BASE_URL`, so its API address can change without rebuilding. I run the migration bundle explicitly before starting the API. Requests time out after 15 seconds; mutations are not automatically retried because a lost response may follow a committed write. Verification is in [PROGRESS.md](docs/PROGRESS.md).
